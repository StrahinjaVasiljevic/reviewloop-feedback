# ReviewLoop — Product Roadmap

> This roadmap reflects product thinking, not a feature wishlist.  
> Every item is tied to a user problem or a metric we need to move.  
> Timelines are directional — they shift based on what we learn.

---

## Where We Are Now (MVP — shipped)

The core feedback loop works end-to-end:  
trigger → survey → classify → route → digest → dashboard.

We have validated that teams will embed the widget, that customers will respond to single-question surveys triggered by behavior, and that PMs will check the inbox weekly if the digest email is clear. The loop is closed. Now we need to make it faster, smarter, and more integrated.

---

## Short-Term: Next Iteration (0–3 months)

**Goal:** Improve the quality and reliability of the core loop. Reduce friction for the PM doing triage.

### 1. Classifier accuracy improvement
- **Problem:** Rules-based tagger misclassifies ~20% of edge-case responses.
- **Approach:** Manual review UI for the PM to correct classifications. Corrections build a labeled dataset for the ML upgrade.
- **Why now:** Every misclassified response erodes trust in the routing. Trust is the product.

### 2. Trigger A/B testing
- **Problem:** We do not know which trigger conditions produce the highest completion rate without degrading the user experience.
- **Approach:** Allow two trigger variants per workspace. Track completion rates per variant. Surface winner after statistical significance.
- **Why now:** Completion rate is a leading indicator of North Star movement. Small gains here compound.

### 3. Slack routing integration
- **Problem:** PMs already live in Slack. The inbox is one more tab to check.
- **Approach:** Route classified feedback to a configurable Slack channel. Keep the inbox as the system of record.
- **Why now:** Multiple pilot customers asked for this unprompted. When customers align on a request, it is prioritized.

### 4. Response tagging and search
- **Problem:** PMs can see themes but cannot quickly find all responses related to a specific feature or customer segment.
- **Approach:** Free-text search on response content + manual tag application. No AI, no complexity — just search.
- **Why now:** Without search, the inbox becomes unusable past 500 responses. We are approaching that threshold.

## Mid-Term: Scaling & Deepening Value (3–9 months)

**Goal:** Make ReviewLoop the connective tissue between customer feedback and the product team's existing workflow.

### 1. Linear and Jira integration
- **Problem:** Insights from ReviewLoop live in a silo. Linking them to tickets requires manual copy-paste.
- **Approach:** Allow a PM to push a feedback theme to a Linear/Jira ticket with one click, preserving the source responses as context.
- **Why this, why now:** This closes the accountability loop. When engineers can see the raw customer words behind a ticket, prioritization conversations change.

### 2. ML-based classifier (v1)
- **Problem:** The rules-based classifier does not generalize to new product areas or new customer segments.
- **Approach:** Train a lightweight text classification model on the labeled dataset generated by correction UI (Short-Term item 1). Fine-tune on domain-specific SaaS vocabulary.
- **Dependencies:** Requires ~2,000 labeled examples. We will have that by month 4 at current response volume.

### 3. Customer segmentation on feedback
- **Problem:** Feedback from a power user and a churned trial user should not carry the same weight in product decisions.
- **Approach:** Accept customer attributes on the widget initialization (plan, tenure, ARR tier). Filter and segment the dashboard by these dimensions.
- **Why this matters:** A churn signal from a $50k ARR customer is a five-alarm fire. The same signal from a free-tier user is a different conversation.

### 4. Churn prediction score
- **Problem:** The current churn-risk flag is binary (flag / no flag). It is useful but blunt.
- **Approach:** Build a simple churn propensity score using sentiment trend, response frequency drop, and login cadence (requires read-only product analytics integration). Score 1–10, surfaced on the customer profile view.
- **Why now (mid-term, not short-term):** This requires external data integration and model validation. Building it before the classifier is solid would layer complexity on an unstable foundation.

### 5. Self-serve onboarding
- **Problem:** Onboarding currently requires a 30-minute setup call. That does not scale.
- **Approach:** Interactive setup wizard: embed the script tag, configure first trigger, preview the widget, send a test response — all in-product, under 10 minutes.
- **Why this belongs in mid-term:** Until we understand the common failure points in onboarding (we will know by month 3), building a wizard is building for the wrong problems.

## Long-Term: Product Vision (9–24 months)

**Goal:** Become the operating system for customer-led product decisions in B2B SaaS.

### Vision statement
Most product teams make decisions based on the loudest voice in the room — usually sales, occasionally CS, rarely the actual customer. ReviewLoop's long-term vision is to make the customer's voice the default input to every sprint planning, roadmap prioritization, and go/no-go decision — automatically, without requiring a dedicated researcher or analyst.

### Strategic bets

**1. Feedback as a graph, not a list**  
Connect individual responses to customer journeys, feature adoption, and revenue data. Move from "what are customers saying" to "what are customers who expand their contracts saying, and why."

**2. Proactive insight surfacing**  
Stop requiring the PM to check the dashboard. Push actionable insights to the team at the moment they are relevant — before sprint planning, before a renewal conversation, before a feature launch.

**3. Benchmark network**  
Aggregate anonymized, opt-in data across workspaces to offer industry benchmarks. "Your churn-risk rate is 2.3x the SaaS median for your ARR tier" is a conversation-starter that sells the product and drives urgency.

**4. Researcher-grade qualitative tools**  
When quantitative signal flags a theme, the PM needs to go deep. Build a lightweight interview scheduling and synthesis layer — not to replace dedicated research tools, but to close the gap between "we see a pattern" and "we understand it."

### What we will not build (intentionally)
- A full CRM. We plug into CRMs; we do not replace them.  
- A community or forum product. Different feedback modality, different buyer, different motion.  
- An AI chatbot for customers. High noise, low signal, misaligned with our positioning.
